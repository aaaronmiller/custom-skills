## 1. Design Philosophy

**Q-001 (targets F-002, F-003):**
The dream agent's budget formula (idle_seconds × 0.25, capped at 7200s) allocates 25% of idle time to wiki processing. Should this be a fixed percentage, or should it be adaptive based on the backlog of unprocessed ClawMem entries and the current wiki quality score? What metric would you use to determine the right fraction?

**Q-002 (targets F-015, F-024):**
The vault improvement engine currently only fixes structural issues (missing frontmatter, broken links, stale dates). The S-tier reference-based embedding improvement is specified but not implemented. Should the quality-compounding loop be built around embedding distance to reference documents, or is there a better approach — perhaps LLM-judged rubric scoring, or human-curated quality gates? What approach would produce the most reliable quality gains for the least compute cost?

## 2. Architecture

**Q-003 (targets F-001):**
The three-tier architecture (ClawMem → Wiki Pages → MemVid) treats compiled wiki pages as the permanent "warm" layer between hot memory and cold archival. Could the compiled wiki pages serve as the cold storage directly (eliminating MemVid as a separate tier), or is the video-codec compression of MemVid essential for the multi-resolution archival use case? What would be lost by collapsing to two tiers?

**Q-004 (targets F-002, F-004):**
The dream agent reads ClawMem exclusively via REST API. This adds network overhead and serialization cost. Given that both run on the same machine in the reference setup, would direct SQLite access be more appropriate, or does the REST API abstraction provide essential decoupling (e.g., for running ClawMem remotely, or replacing it)? Under what conditions does the REST API become a bottleneck?

**Q-005 (targets F-007, F-020):**
Idle detection uses loginctl (Linux-only), making cross-platform support incomplete. What would be the most practical cross-platform idle detection strategy — polling /dev/input on Linux, IOKit on macOS, GetLastInputInfo on Windows, or a middleware layer that abstracts all three? Should idle detection even be the trigger, or would a calendar-based schedule (e.g., "run every night at 2 AM") be more reliable across platforms?

## 3. Feature Scope

**Q-006 (targets F-014):**
Auto-skill creation from patterns triggers at 3 occurrences of a task type. Is creating a SKILL.md the right output for pattern detection, or should the system instead compile patterns into wiki pages (documenting "how we do X" as knowledge rather than as agent instructions)? What are the risks of auto-generating skills that are too specific or too generic?

**Q-007 (targets F-006, F-023):**
The wiki page compilation writes YAML frontmatter with confidence scores, provenance, and wikilinks. Should compiled pages also include a human-readable "why this was compiled" section — e.g., "This page was auto-generated from 3 ClawMem entries about the event sourcing migration between 2026-05-10 and 2026-05-20. Confidence: 0.82 based on 4 supporting claims, 0 contradictions."?

**Q-008 (targets F-013):**
The wiki MCP server is specified but disabled, offering three tools: wiki_search, wiki_query, wiki_ingest. Is an MCP server the right interface for wiki access, or would a simpler approach (e.g., a shell command that greps the wiki directory, or an HTTP endpoint that serves the markdown files) be more practical given the wiki is already a filesystem of markdown files? What unique value does the MCP interface provide over direct filesystem access?

## 4. Tradeoffs

**Q-009 (targets F-005, F-022):**
Confidence scoring uses four weighted factors (35% self-consistency, 25% freshness, 25% cross-ref agreement, 15% evidence count). Are these weights optimal, and what evidence supports them? Should confidence be recalculated as new evidence arrives (e.g., a later session that confirms or contradicts an earlier claim), making it a dynamic rather than static score?

**Q-010 (targets F-008, F-012):**
The multi-agent integration uses symlinks to share skills across 7 agents. Symlinks are simple but fragile — a user deleting their ~/.claude/skills/ directory loses the link, and the setup script must recreate it. Would a shared skill registry (a single file that agents read to discover skills) be more robust than filesystem symlinks? What are the failure modes of the symlink approach?

## 5. Gaps

**Q-011 (targets F-005):**
The council escalation for contradictory claims is a stub that always returns True (accepts). This means contradictory claims currently bypass the only safety valve. What should the adversarial deliberation look like in practice — two LLMs debating for/against the claim, a single model analyzing both sides and producing a consensus, or a multi-agent council? How should the system handle the case where deliberation itself is inconclusive?

**Q-012 (targets F-015, F-016):**
The lint engine finds broken links, orphans, and stale drafts but can't fix them. The improvement engine fixes structural issues but can't detect them on its own (it relies on the lint engine being run first). Should lint and improve be merged into a single phase where detection and fix are coupled? What proportion of lint issues should be auto-fixable vs requiring human judgment?

## 6. Prioritization

**Q-013 (targets F-002, F-014, F-015, F-021, F-013, F-022):**
If you could only implement 3 of the following by next release, which 3 and why?
(a) S-tier reference improvement engine
(b) Working council deliberation stub
(c) Wiki MCP server
(d) MemVid cold storage integration
(e) Intent router implementation in-wiki
(f) Cross-platform idle detection

Rank them and defend the priority.

**Q-014 (targets F-006, F-016, F-017):**
The wiki contains zero automated tests across all 24 features. Given limited development time, what's the highest-leverage testing strategy — integration tests for the dream cycle pipeline, unit tests for the confidence scoring math, property-based tests for the wiki page compilation (idempotency, provenance preservation), or snapshot tests comparing cycle outputs against known-good results? Which testing approach would catch the most damaging regressions first?

## 7. Alternatives

**Q-015 (targets F-001, F-002):**
The entire system is premised on three independent storage backends orchestrated by a Python sidecar. What would this look like as a single-process SQLite extension with embedded vector search — i.e., collapsing the dream agent into ClawMem itself as a background job, and eliminating both the REST API boundary and the separate Python process? What is lost and gained in that unification?
