# Karpathy Wiki — Spec As Built v1.0

_Generated by spec-audit-skill Phase 1. Date: 2026-05-22._

## Overview

The Karpathy Wiki is an auto-compiling knowledge system that transforms raw session data, notes, and project artifacts into a structured, permanent wiki — then continuously improves that wiki during idle compute cycles. It's designed for development teams and knowledge workers who want their accumulated context to survive session boundaries and compound in quality over time without manual documentation effort.

The system unifies three memory tiers (Hot → Warm → Cold) through an orchestration layer, treating the knowledge base as "shared RAM" for LLM-human collaboration. The core premise: quality compounds over time without human effort if you build the right pipelines.

### F-001: Three-Tier Memory Architecture (Hot → Warm → Cold)

- **What:** The system stores and retrieves knowledge across three tiers with different latency, capacity, and persistence characteristics — ClawMem (hot/warm, sub-ms SQLite + vector), MemVid V2 (cold archival, video-codec compressed), and compiled wiki pages (permanent, human-readable).
- **Why:** No single storage technology is optimal for all access patterns. Hot data needs instant retrieval, cold data needs efficient compression, and permanent knowledge needs human readability and git history. The tiered approach lets each tier optimize for its job.
- **Where:** `config.schema.yaml`, `specs/design.md`, `specs/requirements.md`, `dream/dream_agent.py`
- **Dependencies:** None (foundational)
- **Quality:**
  - Completeness: **high** — three tiers clearly defined with data flow between them
  - Consistency: **good** — tiers have clear boundaries and transition rules
  - Tests: **no** — no automated tests verifying tier transitions or data fidelity across tiers

### F-002: Autonomous Dream Agent (Sleep-Time Compute)

- **What:** A Python sidecar that runs during idle system cycles, executing a 6-phase pipeline: Budget Allocation → Extract (from ClawMem) → Refine (confidence scoring + council escalation) → Compile (write wiki pages) → Pattern Detect (auto-skill creation) → Re-index → Improve (vault quality engine).
- **Why:** Session data accumulates faster than humans can process it. The dream agent turns idle compute cycles into wiki improvement without any human intervention — the system gets smarter while you sleep.
- **Where:** `dream/dream_agent.py` (entire file, ~1085 lines)
- **Dependencies:** F-001 (memory tiers), F-004 (ClawMem REST API), F-008 (deliberative refinement)
- **Quality:**
  - Completeness: **high** — all 6 phases implemented with graceful degradation when ClawMem is unavailable
  - Consistency: **good** — phases are sequential with clear data flow (claims → refined claims → pages → patterns → improvements)
  - Tests: **no** — no unit tests or integration tests for any dream cycle phase

### F-003: Budget Allocation Based on Idle Time

- **What:** The dream agent calculates its resource budget as `idle_seconds × 0.25`, capped at 7200s (2h). The intake/compile/improve ratio shifts dynamically: 80/20 at raw (early wiki), 50/50 at mid, 33/67 at mature. Each phase enforces its own sub-budget.
- **Why:** Without budget limits, the dream agent would consume all available CPU/GPU. The dynamic ratio reflects that mature wikis need more improvement than intake, while new wikis need more intake to populate pages.
- **Where:** `dream/dream_agent.py` (allocate_budget function)
- **Dependencies:** F-002
- **Quality:**
  - Completeness: **high** — ratio-shifting logic, per-phase budgets, total cap
  - Consistency: **good**
  - Tests: **no**

### F-004: ClawMem REST API Integration

- **What:** The dream agent reads from and writes to ClawMem exclusively via REST API (`GET /documents/:docid`, `POST /search`, `POST /reindex`). Never accesses ClawMem's SQLite database directly.
- **Why:** Decoupling via REST API means the dream agent doesn't depend on ClawMem's internal storage format. ClawMem can be replaced, upgraded, or run on a different machine without changing the dream agent.
- **Where:** `dream/dream_agent.py` (json_post helper, all ClawMem interaction functions)
- **Dependencies:** F-001, external dependency on ClawMem running at `localhost:7438`
- **Quality:**
  - Completeness: **high** — search, retrieve, reindex covered
  - Consistency: **good**
  - Tests: **no**

### F-005: Deliberative Refinement Confidence Scoring

- **What:** Claims extracted from sessions are scored on four weighted factors: 35% self-consistency, 25% source freshness, 25% cross-reference agreement, 15% evidence count. Thresholds: >0.8 auto-compile to wiki, 0.5–0.8 flag for human review, <0.5 reject. Claims in the `[0.5, 0.6]` range that contradict existing high-confidence content trigger council escalation (two-model adversarial deliberation).
- **Why:** Not all claims are equally trustworthy. The weighted scoring prevents low-quality or contradictory information from entering the permanent wiki while still capturing uncertain claims where they can be reviewed. The council escalation is the safety valve for genuinely contentious information.
- **Where:** `dream/dream_agent.py` (refine_claim, _check_cross_ref_agreement, _contradicts_existing_high_confidence, _convene_council, global CONFIDENCE_* constants)
- **Dependencies:** F-002, F-014 (council stub)
- **Quality:**
  - Completeness: **medium** — the four weighted factors are implemented, but council escalation is a stub that always returns True (accepts). The adversarial deliberation isn't actually wired up.
  - Consistency: **good** — thresholds are clear and consistently applied
  - Tests: **no**

### F-006: Wiki Page Compilation with Full YAML Frontmatter

- **What:** Compiled wiki pages include YAML frontmatter with title, created/updated dates, tags, confidence score, status (stable/draft/needs_review/stale), sources (ClawMem docid URIs), wikilinks to related entities and concepts, and entity types.
- **Why:** Every wiki page must be self-describing — a human or agent reading it can immediately see where the information came from, how reliable it is, and what other pages relate to it. This is the provenance chain made visible.
- **Where:** `dream/dream_agent.py` (compile_to_wiki, _build_frontmatter, _build_body, _find_or_create_page)
- **Dependencies:** F-002, F-005
- **Quality:**
  - Completeness: **high** — all frontmatter fields implemented, page creation/update logic, entity/concept-based directory routing
  - Consistency: **good** — matches the schema defined in AGENTS_WIKI.md
  - Tests: **no**

### F-007: Idle Detection via Scheduler Daemon

- **What:** A scheduler daemon (`scheduler.py`) runs on systemd idle timer (30-minute check, 5-minute idle threshold). It uses `loginctl` to detect user idle state, persists state to `scheduler_state.json`, and triggers dream cycles with configurable idle thresholds (default 600s).
- **Why:** The dream agent should only run when the system is actually idle — not competing with the user's active work. `loginctl` is a platform-standard way to check idle state on Linux.
- **Where:** `dream/scheduler.py`
- **Dependencies:** F-002, systemd/loginctl on Linux
- **Quality:**
  - Completeness: **medium** — basic daemon loop works but has no cross-platform support (macOS/Windows don't have loginctl)
  - Consistency: **good**
  - Tests: **no**

### F-008: Multi-Agent Support (7 Agents)

- **What:** The wiki integrates with 7 agents/tools: Pi Agent, Claude Code, Ante, Hermes, KiloCode, OpenCode, and Antigravity. Each gets skill symlinks, MCP registration, and optionally hooks. Configurable per-agent in `config.schema.yaml`.

- **Where:** `config.schema.yaml` (agents section), `install.sh`
- **Dependencies:** F-012 (symlink management), F-013 (MCP registration)
- **Quality:**
  - Completeness: **high** — all 7 agents listed with distinct integration patterns
  - Consistency: **good** — each agent has clear config keys, no overlap or ambiguity
  - Tests: **no**

### F-009: Configuration Presets (4 Profiles)

- **What:** Four named presets override config defaults: `lightweight` (CPU-only, minimal models, single-agent), `balanced` (GPU-assisted, default), `high-quality` (full RAG, vLLM, all agents), `max-context` (all encodings, 8h budget, deep archive). Each preset adjusts ClawMem profile, embedding dimensions, model sizes, enabled agents, and time budgets.
- **Why:** Different hardware needs different configurations. A laptop with 8GB RAM can't run the same setup as a workstation with 24GB VRAM. Presets let users pick the right profile without understanding every config knob.
- **Where:** `config.schema.yaml` (presets section, ~200 lines)
- **Dependencies:** F-001, F-002, F-003, F-008, F-010, F-011
- **Quality:**
  - Completeness: **high** — four well-differentiated presets
  - Consistency: **good** — presets stack as overrides on defaults
  - Tests: **no**

### F-010: Configurable LLM Backend

- **What:** Five providers configurable at runtime: vLLM, llama.cpp, MLX, OpenAI, Anthropic. Each has provider-specific defaults (URL, model, health endpoint). Additionally supports per-component model overrides (classification, embedding) and GPU/CPU-specific fallback models for classifiers.
- **Why:** No single LLM provider is optimal for every task or every hardware setup. Configurable backends let users choose cost/quality tradeoffs, use local models for privacy, and fall back to smaller models on CPU when GPU is unavailable.
- **Where:** `config.schema.yaml` (llm_backend section)
- **Dependencies:** F-009 (presets set provider defaults)
- **Quality:**
  - Completeness: **high** — five providers, per-component overrides, hardware fallback models
  - Consistency: **good** — provider-agnostic interface
  - Tests: **no**

### F-011: Embedding and Reranking Pipeline

- **What:** Configurable embedding provider (default: llama.cpp at :8088, 768 dims) with hybrid search (BM25 0.4 + vector 0.6 weight). Cross-encoder reranking with configurable top_k (20 → final 5), recency boost (1.2x for <30min), batch processing (50 docs every 60min), and 24h cache.
- **Why:** Raw vector search misses keyword matches. BM25 alone misses semantic matches. Hybrid search + reranking gives the best of both, and the reranking cache prevents recomputation.
- **Where:** `config.schema.yaml` (classifier.retrieval, rerank sections)
- **Dependencies:** F-001 (ClawMem tier uses this pipeline)
- **Quality:**
  - Completeness: **high** — all major parameters configurable, recency boost, caching
  - Consistency: **good**
  - Tests: **no**

### F-014: Auto-Skill Creation from Detected Patterns

- **What:** Phase 4 of the dream cycle scans claims for repeated task patterns (code-review, deployment, testing, debugging, database, api-development, research). When a pattern reaches 3 occurrences, it auto-generates a SKILL.md with a procedure template, triggers, pitfalls, and verification steps — then writes it to Pi's skills directory and the wiki.
- **Why:** If the same type of task appears repeatedly in sessions, it should be captured as a reusable skill. This is the system learning from usage patterns without explicit instruction.
- **Where:** `dream/dream_agent.py` (detect_patterns, _create_skill_from_pattern, template dictionary)
- **Dependencies:** F-002
- **Quality:**
  - Completeness: **high** — 7 detection patterns, template system, wiki write, Pi skills directory write, logging
  - Consistency: **medium** — templates are hardcoded strings in the Python file rather than loaded from config. Adding new patterns requires code changes.
  - Tests: **no**

### F-015: Vault Improvement Engine (Phase 6)

- **What:** After compilation, Phase 6 scans existing wiki pages for structural issues (missing confidence, missing status, missing sources, broken wikilinks, stale dates). Fixes issues automatically up to 5 per cycle within budget. Uses embedding-guided gap analysis (scaffolding) and logs improvement candidates.
- **Why:** Wiki pages degrade over time as the schema evolves or links break. The improvement engine catches common structural rot and fixes it without human attention.
- **Where:** `dream/dream_agent.py` (improve_wiki, _find_improvement_candidates)
- **Dependencies:** F-002, F-003
- **Quality:**
  - Completeness: **medium** — structural fixes work but the embedding-guided gap analysis is scaffolding (logs candidates but uses simple regex checks). Full S-tier reference-based improvement is not wired up.
  - Consistency: **good**
  - Tests: **no**

### F-016: Lint Engine

- **What:** Post-cycle check that finds orphan pages (not referenced in index.md), broken wikilinks ([[links]] to pages that don't exist), stale drafts (status=draft older than 30 days), and contradictions with high-confidence pages. Issues are logged in the cycle report.
- **Why:** Wikis rot silently without maintenance. The lint engine surfaces problems the improvement engine can't fix automatically — so a human (or future automation) knows what needs attention.
- **Where:** `dream/dream_agent.py` (lint_wiki)
- **Dependencies:** F-002
- **Quality:**
  - Completeness: **high** — orphan detection, broken link detection, stale draft detection, contradiction detection
  - Consistency: **good**
  - Tests: **no**

### F-019: Session Hooks (Pre-Compact and Session-End)

- **What:** Two Python hooks (`hooks/pre_compact.py`, `hooks/session_end.py`) are installed into agent session lifecycles. The pre-compact hook captures current session context before context compaction, saving it to the wiki's `raw/` directory. The session-end hook captures final session state.

### F-021: Intent Router (Classification-Based Memory Routing)

- **What:** A two-stage query intent classifier: heuristic regex (0ms, covers ~70% of queries) and LLM refinement for ambiguous queries. Maps intent to tier routing: "recent" → ClawMem only, "relational/why" → ClawMem + graph, "entity" → ClawMem + graph, "historical/archival" → ClawMem + MemVid, "ambiguous" → all tiers. Results cached per session.
- **Why:** Not all queries need all memory tiers. Classification avoids wasted compute — a question about today's error doesn't need to search cold storage archives.
- **Where:** `config.schema.yaml` (intent_router section), referenced in `specs/design.md` and `specs/requirements.md`
- **Quality:**
  - Completeness: **medium** — config schema defines it clearly, but the actual heuristic + LLM classifier implementation is in ClawMem (external dependency), not in the wiki codebase itself. The wiki codebase has the config knobs but not the implementation.
  - Consistency: **good**
  - Tests: **no**

### F-022: Provenance Chain (Cross-Layer Metadata)

- **What:** Every compiled wiki page carries `sources` that link back to ClawMem docids. Cold-stored MemVid entries have `memvid_indices → chunks.metadata_json` that round-trip to original ClawMem entries. A full six-link chain: original session → ClawMem entry → wiki page → cold archive → superseding decision.
- **Why:** Trust requires traceability. If a user can't verify where a claim came from, the wiki is just another black box. The provenance chain means every claim is verifiable back to its original source.
- **Where:** `specs/design.md` (architecture), `specs/requirements.md` (FR-META-001, FR-META-002, FR-META-003), `dream/dream_agent.py` (frontmatter sources field)
- **Quality:**
  - Completeness: **partial** — the ClawMem → wiki page link is implemented (sources in frontmatter). The MemVid chunk metadata chain is specified but not implemented (the memvid_indices join table is documented but the wiki codebase doesn't write to it).
  - Consistency: **good** — what's implemented follows the spec
  - Tests: **no**

### F-024: S-Tier Reference-Based Quality Scoring (Specified)

- **What:** Spec defines that vault documents should be classified by type (project plan, research note, tutorial, code, narrative, etc.) and scored against curated S-tier reference documents using embedding cosine distance as a loss function. Documents reaching ≥90 may trigger proactive execution.
- **Why:** Without a quality metric, "improvement" is random. S-tier references provide a concrete target — a document that scores well is one that structurally resembles an exemplar of its type.
- **Where:** `specs/requirements.md` (FR-IMPROVE-001 through FR-IMPROVE-009), `specs/design.md`
- **Quality:**
  - Completeness: **scaffolding only** — the spec is thorough (9 requirements), but implementation is limited to structural fixes (missing frontmatter, broken links). The embedding-based quality scoring, rubric gap analysis, and S-tier reference comparison are not implemented.
  - Consistency: **good** — the implementation doesn't contradict the spec (it just hasn't reached it yet)
  - Tests: **no**

## Architecture Summary

The Karpathy Wiki is a **pipeline architecture** with a static triple-tier store feeding into an autonomous compilation loop. Data flows in one direction: raw session hooks → ClawMem (hot/warm) → dream agent (compilation) → wiki pages (permanent) → optional cold archive (MemVid). The dream agent is the active component, gated by idle detection. Each agent integration is a passive consumer that benefits from the accumulated knowledge but contributes via session hooks.

The architecture is **monolithic in process** (single Python sidecar) but **distributed in storage** (three independent backends connected by REST APIs and filesystem). This hybrid approach avoids the operational complexity of a fully distributed system while keeping the flexibility of independent storage tiers.

## Observable Patterns

### Design Philosophy

The project follows a **"compounding quality"** philosophy — the core insight is that autonomous background processing can turn session ephemera into permanent knowledge, and that knowledge _compounds_ in quality over time. This is expressed in:

- The shift from intake-heavy to improvement-heavy budget ratios as the wiki matures
- The threshold gating on confidence scores (low confidence rejected, medium flagged, high auto-compiled)
- The vault improvement engine's iteration loop with convergence detection
- The auto-skill creation from detected patterns (the system learns which tasks recur)

### Assumptions

1. **Idle compute is available.** The entire dream agent cycle depends on system idle time. On a system that's never idle (CI servers, always-busy workstations), the dream agent never runs.
2. **ClawMem is the primary intake.** The dream agent only processes what's in ClawMem. If session hooks fail or ClawMem is down, nothing enters the pipeline.
3. **Linux-dominant environment.** Idle detection uses `loginctl` (Linux). macOS and WSL2 support is acknowledged but incomplete.
4. **LLM access is available.** Classification, refinement, and improvement all need an LLM endpoint. Offline or disconnected setups won't function.
5. **Users want auto-generated wiki content.** The entire pipeline assumes compiled knowledge is better than raw session data. Some teams may prefer manual curation.

### Deliberate Omissions

1. **No user-facing UI.** There's no dashboard, no web interface, no notification system. The wiki is files on disk and JSON reports in stdout. This is deliberate — the project targets agent-native consumption, not human-friendly dashboards.
2. **No conflict resolution for contradictory wiki pages.** If two sessions produce contradictory claims that both pass the confidence threshold, both get compiled. The lint engine flags contradictions but doesn't resolve them.
3. **No backup/restore system.** Git provides version history, but there's no snapshot/rollback mechanism beyond git operations. The improvement engine preserves originals with `-improved` suffix but doesn't have a rollback workflow.
4. **No user notification.** The dream agent prints to stdout and logs. There's no email, no push notification, no dashboard showing "your wiki grew by 5 pages today."
5. **No built-in search for compiled wiki pages.** The wiki MCP server is specified (port 7439, tools listed) but not implemented. Users query ClawMem directly for search — the wiki pages are human-readable but not directly searchable through the same interface.
