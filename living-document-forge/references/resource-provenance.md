# Resource and provenance handling

## Storage

Attached files are stored in `resources/` with sanitized names. Manifest `resources` records preserve original filename, kind, extension, media type, size, URL, target IDs, status, and SHA-256 when available.

Keep document evidence separate from application assets. `public/` contains the browser shell and content files; `resources/` contains attachments and media.

## Safety

Treat all attachments as untrusted. Do not execute scripts, installers, macros, archives, or binaries. Inspect Markdown, text, CSV, JSON, images, audio, and video only when relevant and supported by the environment. For archives, list contents before extraction and reject traversal paths. Never upload attached private files to a remote backend unless the request explicitly authorizes that package mode.

## Use in revisions

Record how a resource affected the document:

- evidence for a factual correction;
- reference for visual direction;
- example of mechanism behavior;
- source for a new section;
- objection or alternative;
- artifact to embed or link.

Do not cite a file you did not inspect. Do not infer missing content from its filename.

## Exports

ZIP exports exclude credential stores, run logs, and transient request files. Resources remain included because they are part of the document’s evidence bundle. If a resource has licensing or privacy restrictions, add a manifest note before publication.

## Provenance language

Distinguish:

- created for this project;
- supplied by the user;
- generated by a model;
- adapted from a cited source;
- unknown origin;
- restricted or private.

This distinction should remain visible in worklogs and artifact manifests.
