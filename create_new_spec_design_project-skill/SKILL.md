# Create New Project (v2)

> From brain dump to build-ready specs in one session — using Speckit commands directly.

Transforms raw ideas, transcripts, or existing detailed specifications into Speckit-compatible artifacts (spec.md, plan.md, tasks.md) by invoking `/speckit-specify`, `/speckit-plan`, and `/speckit-tasks` with explicit depth-preservation directives.

## Three Intake Modes

### Mode A: Transcript Processing
**Trigger:** User provides one or more transcripts, voice notes, brain dumps, or unstructured notes.

### Mode B: Interactive Discussion
**Trigger:** User describes an idea verbally or wants to explore/define it through conversation.

### Mode C: Existing Detailed Specifications
**Trigger:** User provides existing, detailed design.md and requirements.md files (or equivalent comprehensive spec documents). Detection: input files are 5K+ with structured requirements (FR-XXX format), component descriptions, and data model sections.

**Mode C behavior:**
- Skip Phase 1 (Intake) — already fully specified
- Skip Phase 2 (Prior Art Research) — already researched
- **Schema completeness check:** If the existing design.md contains a data model with entity descriptions of ≥10 columns per entity AND a primary key definition, schema is considered **complete** → skip Phase 3. If no data model or minimal (<10 columns defined), proceed to Phase 3 to design it.
- In Phase 4, pass existing documents as-is to Speckit commands with explicit depth-preservation instructions
- In Phase 5, run depth-verification gate comparing output against original input

### Fast Track (Mode A or B shortcut)
**Trigger:** User provides a complete, well-structured project description that already covers problem, solution, users, data, constraints, and scope. Simple or well-understood projects (todo apps, CRUD tools, standard integrations) where the user clearly knows what they want.

**Fast track behavior:** Skip the iterative discovery loop. Run the Confidence Gate rubric once. If >= 85% on first pass, proceed directly to Phase 3 (data architecture). If not, drop into Mode B for targeted gap-fill only on sub-threshold dimensions.

All three modes produce identical output written to the existing spec infrastructure:

```
specs/{project-name}/
├── requirements.md         # WHAT and WHY (copied or generated as-is)
├── design.md               # HOW (copied or generated as-is)
├── spec.md                 # Generated by /speckit-specify
├── plan.md                 # Generated by /speckit-plan
├── research.md             # Generated by /speckit-plan
├── data-model.md           # Generated by /speckit-plan
├── contracts/              # Generated by /speckit-plan
├── quickstart.md           # Generated by /speckit-plan
└── tasks.md                # Generated by /speckit-tasks
```

**Output path note:** The `./docs/specs/` path is a fallback default. The skill first checks for existing spec infrastructure in this priority order: `specs/` (SpecKit), `openspec/changes/` (OpenSpec), `.kiro/specs/` (Kiro), then falls back to `docs/specs/`.

## Confidence Gate

Before generating documents, the intake must reach **85% confidence** across eight dimensions. Score conservatively; one extra round of questions costs minutes, a bad spec costs hours.

| Dimension | Weight | 0-25% (Unclear) | 50% (Partial) | 75% (Solid) | 100% (Crystal) |
|-----------|--------|------------------|----------------|-------------|-----------------|
| Problem clarity | 15% | Vague pain point | Problem stated but root cause unclear | Root cause identified with evidence | Quantified impact, clear before/after |
| Solution definition | 15% | "Something like X" | Core concept described | Workflow walkthrough possible | End-to-end user journey articulable |
| User personas | 10% | "People who..." | 1 persona identified | 2-3 personas with distinct needs | Personas with goals, frustrations, context |
| Success criteria | 10% | "It should work" | Qualitative goals | Measurable outcomes defined | Testable metrics with targets |
| Data model | 15% | No entities discussed | Some entities named | Entities + relationships clear | Access patterns + lifecycle defined |
| Scope boundaries | 10% | Open-ended | Some exclusions stated | In/out scope list exists | Boundary rationale documented |
| Technical constraints | 10% | None stated | Platform mentioned | Platform + perf + integration clear | Full constraint matrix |
| Business context | 15% | None | Open source vs commercial decided | Distribution + monetization clear | Competitive position articulated |

**When confidence < 85%:** Ask 3-5 structured questions per round targeting the lowest-scoring dimensions. Reassess after each round. Do not proceed until threshold is met.

**When confidence >= 85%:** Proceed to Phase 3. Note any dimensions below 75% as items requiring `[NEEDS CLARIFICATION]` markers in the requirements document.

## Execution Protocol

### Phase 0: Mode Detection and Setup

1. **Detect mode** from user input:
   - Files/transcripts provided → Mode A
   - Verbal description or "I want to build X" → Mode B
   - Mixed (some notes + wants to discuss) → Mode A first, then Mode B gap-fill
   - Existing detailed design.md + requirements.md provided (each 5K+) → **Mode C**

2. **Load references:**
   - Read `references/requirements-template.md` for requirements format
   - Read `references/design-template.md` for design format
   - Read `references/research-checklist.md` for prior art research protocol
   - Read `references/data-architecture-guide.md` for schema/hosting decisions
   - Read `references/constitution.md` for constitutional governance reference

3. **Check for user preferences** in memory/context:
   - Preferred stack (frameworks, languages, deployment targets)
   - Design language preferences (Material, shadcn, custom)
   - Hosting preferences (Cloudflare, Vercel, self-hosted)
   - These inform the design document but do NOT appear in the requirements document (requirements are technology-agnostic per SDD principles)

4. **Codebase exploration** (if inside an existing project):
   - Scan for existing architecture patterns, package managers, frameworks in use
   - Check for `.specify/memory/constitution.md` (project-specific governance), `specs/`, `openspec/`, `.kiro/` directories
   - Detect constitution.md or equivalent governance files
   - Note existing dependencies, test frameworks, deployment configs
   - Do NOT write exploration findings to files; they are context for the ideation process, not an artifact

5. **Feature directory detection:**
   - If a numbered feature directory already exists under `specs/` (e.g. `specs/001-quartermaster/`), use it
   - If not, `/speckit-specify` will create one in Phase 4

6. **If Mode C:**
   - Confirm existing documents are adequate with the user
   - Skip directly to Phase 3 (data architecture if schema missing) or Phase 4
   - Note: Mode C does NOT use the Confidence Gate — the existing documents already represent verified requirements

### Phase 1: Intake and Extraction

> **Skip in Mode C** — existing documents are already fully specified.

#### Mode A: Transcript Processing

1. **Read all provided transcripts/files**
2. **Extract structured signals:**
   - Problem statements (what pain exists)
   - Proposed solutions (what the user wants to build)
   - User types / personas mentioned
   - Success criteria (how "done" is defined)
   - Constraints mentioned (budget, timeline, platform, privacy)
   - Data entities and relationships implied
   - Integration points mentioned (APIs, services, platforms)
   - UX/workflow descriptions
3. **Compute confidence score** using the Confidence Gate rubric above
4. **If confidence < 85%:** Switch to Mode B for gap-filling discussion, targeting lowest-scoring dimensions
5. **If confidence >= 85%:** Proceed to Phase 2 with extracted signals

**Tool guidance:** When available, use structured input tools (AskUserQuestion, ask_user_input) to present clarifying questions with selectable options rather than open-ended text prompts. This reduces friction and prevents misinterpretation.

#### Mode B: Interactive Discussion

Conduct a structured discovery conversation. Do NOT ask all questions at once. Proceed through these categories sequentially, asking 2-4 questions per category, adapting based on answers:

**Category 1: Problem Space**
- What problem does this solve? Who has this problem?
- What happens today without this solution?
- What existing tools/approaches do people use now, and why are they insufficient?

**Category 2: Solution Vision**
- What does success look like for the user of this tool/product?
- Walk through the primary user workflow from start to finish
- What is explicitly out of scope for v1?

**Category 3: Users and Adoption**
- Who are the 1-3 primary user types?
- What is the user's technical sophistication level?
- How will users discover and adopt this? (distribution channel)
- What would make a user choose this over alternatives?

**Category 4: Data and State**
- What data does the system need to store?
- What are the relationships between data entities?
- What is the data lifecycle (created, read, updated, deleted, archived)?
- What are the privacy/retention requirements?

**Category 5: Technical Constraints**
- Target platforms (web, mobile, desktop, CLI, embedded)?
- Offline capability requirements?
- Performance expectations (latency, throughput, scale)?
- Integration requirements (what existing systems must it connect to?)

**Category 6: UX and Interaction Model**
- What interaction pattern fits best (CRUD app, conversational, dashboard, real-time, wizard)?
- What design language aligns with the audience?
- What accessibility requirements exist?
- How does error handling surface to users?
- Does the project need responsive/adaptive layouts, PWA support, or offline-first UX?
- Are there internationalization (i18n) or localization requirements?

**Category 7: Business and Distribution**
- Is this open source, commercial, or internal?
- What is the monetization strategy (if any)?
- What is the competitive landscape?
- What regulatory/compliance requirements exist?

**Exit condition:** When the Confidence Gate rubric scores >= 85% across all dimensions. After each category round, reassess the confidence score. When threshold is met, confirm with the user: "I have enough clarity to write the spec documents. Here's what I understand: [1-paragraph summary]. Should I proceed?"

**Done criteria per category:**
- Problem Space: Can articulate the problem to a stranger in 2 sentences
- Solution Vision: Can walk through the primary workflow step by step
- Users: Can name each persona and explain why they care
- Data: Can draw an entity-relationship sketch
- Technical: Can list hard constraints vs preferences
- UX: Can describe the first 30 seconds of user interaction and the primary navigation model
- Business: Can explain who pays (or why it is free) and how users find it

### Phase 2: Prior Art Research

> **Skip in Mode C** — existing documents already reflect prior art research.

**This phase is mandatory for Modes A and B.** Conduct research before writing any spec documents.

Read `references/research-checklist.md` for the full protocol. Summary:

1. **Local workspace scan:**
   - Check for existing agent configs, skills, related projects
   - Check skillshare registries, skills.sh, agentskills.io

2. **GitHub/community search** (minimum 3 searches):
   - Direct competitors or existing solutions
   - Libraries/frameworks that solve sub-problems
   - Similar architectural patterns

3. **Web search** (minimum 2 searches):
   - State of the art in the problem domain
   - Recent developments that could affect approach
   - Community discussions about the problem space

4. **Synthesis:**
   - If existing tools fully solve the problem: surface them immediately, ask user if they still want to proceed
   - If existing tools partially solve: incorporate learnings, note what this project adds beyond them
   - Document findings in the requirements file's "Prior Art" section
   - Extract useful patterns, pitfalls to avoid, and architectural lessons

### Phase 3: Data Architecture Decision

Read `references/data-architecture-guide.md` for the full decision framework.

Based on extracted entities and relationships:

1. **Classify data relationships:**
   - Flat/simple → key-value or document store
   - Relational with joins → SQL (PostgreSQL, SQLite)
   - Graph-like relationships → graph DB or relational with careful schema
   - Time-series dominant → time-series DB or partitioned tables
   - Unstructured/search-heavy → vector store or full-text search engine

2. **Design initial schema** (entity names, key attributes, relationships)
3. **Identify access patterns** (read-heavy, write-heavy, mixed)
4. **Determine storage strategy** (local-first, cloud, hybrid)
5. **Document in design file** with rationale for each decision

**Constitutional check:** Read `references/constitution.md` and the project's `.specify/memory/constitution.md` (if present). Verify all data architecture decisions are consistent with constitutional principles (provenance, local-first source of truth, etc.).

### Phase 4: Speckit Command Pipeline

> **THIS IS THE KEY PHASE.** Instead of generating documents manually from templates, invoke the actual Speckit commands to produce all output files. Each command call MUST include explicit depth-preservation instructions.
>
> **IMPORTANT: Speckit commands (like `/speckit-specify`) may not be available as executable slash commands in all environments.** They are defined as SKILL.md instruction files in the project's `.agents/skills/` directory. To invoke them:
> 1. **If available as slash commands** (e.g., in the quartermaster project context): invoke them directly with the depth-preservation directive as documented below
> 2. **If not available as slash commands**: read the Speckit SKILL.md file from `.agents/skills/speckit-*/SKILL.md` and implement its instructions MANUALLY, applying the depth-preservation directives documented below to every output file

#### 4a. Prepare Input Files

- If Mode A/B: Write intake signals to `requirements.md` and `design.md` in the feature directory (using templates from `references/` for structure, but preserving ALL intake depth — no summarization)
- If Mode C: Copy the existing detailed `requirements.md` and `design.md` into the feature directory (they already have full depth)

The feature directory is `specs/{NNN}-{feature-name}/` (where Speckit commands expect it). If no numbered feature directory exists yet, check what the next available sequence number is (e.g., find existing `specs/0NN*/` directories and increment), then create `specs/{NNN}-{short-name}/` and copy source files there.

#### 4b. Invoke `/speckit-specify`

**Input:** The full content of `requirements.md` (or the extracted feature description from intake).

**Command usage:**
```
/speckit-specify
```

Provide the feature description as `$ARGUMENTS` with this explicit depth-preservation directive prepended:

```
[DEPTH-PRESERVATION DIRECTIVE]
The following is a COMPLETE, DETAILED requirements document. This is a PRECISION PRESERVATION task, not a summarization task.
You MUST:
- Include EVERY functional requirement (FR), acceptance scenario, and edge case from the source
- Do NOT truncate, condense, or summarize any section
- Each FR must retain its full acceptance criteria, preconditions, postconditions, and error paths
- The output spec.md must be at minimum as detailed as the source requirements
- After generating, verify: count of FRs in output vs count in source — they must match
- If the template does not have room for all FRs, extend the template rather than dropping FRs
- Preserve ALL non-functional requirements (NFRs) in full
[/DEPTH-PRESERVATION DIRECTIVE]
```

**After command:** Verify that spec.md contains all FRs from requirements.md. If any are missing, regenerate with explicit reference to the missing sections.

#### 4c. Invoke `/speckit-plan`

**Input:** The existing `spec.md` (generated above) plus the full `design.md` as additional context.

**Command usage:**
```
/speckit-plan
```

Provide the design content as context with this depth-preservation directive:

```
[DEPTH-PRESERVATION DIRECTIVE]
The project already has a COMPLETE, DETAILED design document at design.md.
This is a PRECISION PRESERVATION task, not a summarization task.
You MUST:
- Include EVERY component specification, interface definition, algorithm description, and edge case from the source design.md
- Preserve ALL trade-off analysis and architecture decision rationale
- Include the full data model with ALL entities, relationships, constraints, and access patterns
- The output plan.md must cover ALL sections from the source design — verify section-by-section
- Generate ALL auxiliary files that /speckit-plan normally produces (research.md, data-model.md, contracts/, quickstart.md)
- Populate each auxiliary file with the FULL depth from the source design — no truncation
- If any design section has no counterpart in the plan template, ADD a custom section rather than dropping the content
[/DEPTH-PRESERVATION DIRECTIVE]
```

**After command:** Verify that plan.md covers every section from the source design.md. If architecture overview, component specifications, or data model sections are missing or thinned, regenerate.

#### 4d. Invoke `/speckit-tasks`

**Input:** The existing `spec.md` + `plan.md` (generated above), with explicit cross-reference to the original detailed `design.md`.

**Command usage:**
```
/speckit-tasks
```

Provide this depth-preservation directive:

```
[DEPTH-PRESERVATION DIRECTIVE]
The design specification for this project is extremely detailed (reference: design.md in the feature directory).
This is a PRECISION PRESERVATION task, not a summarization task.
You MUST:
- For EACH task, cross-reference the specific section in design.md that defines what must be implemented
- Include the algorithmic complexity, interface contract, and edge case handling requirements from the source design
- Do NOT reduce any task to just "implement X in file Y" — each task must carry its full specification depth
- Preserve ALL FR-to-task mapping — every FR from spec.md must be traceable to at least one task
- Preserve ALL NFRs as explicit constraints on relevant tasks
- Include error handling, performance requirements, and security considerations from the design in the relevant tasks
- If the tasks template limits task descriptions, EXTEND descriptions rather than truncating them
- For each task, include at minimum: (1) file path, (2) function/interface contract, (3) algorithm description, (4) edge cases to handle, (5) error conditions, (6) acceptance criteria
- Task descriptions MUST average at least 80 words per task (measured in words, not characters or lines). A task with only file paths and stub descriptions (<80 words average across all tasks) indicates depth loss.
[/DEPTH-PRESERVATION DIRECTIVE]
```

**After command:** Verify that tasks.md covers every component, interface, and data entity from design.md. If any design section has no corresponding task, flag and regenerate.

### Phase 5: Deliberative Refinement and Depth Verification

After Speckit command pipeline completes, invoke the **deliberative-refinement** skill with expanded scope:

#### 5a. Format and Consistency Checks (from original skill)

1. **Requirements file (spec.md):** Focus on completeness of requirements, testability, ambiguity detection, missing edge cases, scope creep indicators. Verify every FR has acceptance criteria. Verify no implementation details leaked into requirements. Check for internal contradictions.

2. **Plan file (plan.md):** Focus on architectural soundness, technology fit, scalability concerns, security gaps, missing error handling, deployment feasibility. Verify schema supports all FRs. Verify hosting strategy aligns with NFRs. Check for over-engineering.

3. **Cross-document validation:**
   - Every FR in spec.md has a corresponding section in plan.md
   - Plan does not introduce requirements not present in spec.md
   - Success criteria from spec.md are achievable with proposed architecture
   - Risk mitigations in plan.md address risks identified in requirements

#### 5b. Depth-VERIFICATION Gate (NEW — CRITICAL)

This gate prevents the exact failure that occurred in v1 of this skill. After all Speckit commands have completed:

1. **Compare FR count:** Count FRs in the original requirements.md (or input source) vs FRs in spec.md. Flag if > 10% missing.

2. **Compare design sections:** List every major section heading in the original design.md. Check each against plan.md. Flag any section with no counterpart in plan.md.

3. **Compare entities:** List every data entity from the original design's data model. Check each against data-model.md and tasks.md. Flag any entity that appears in design but is absent from tasks.

4. **Component coverage:** List every component/module from the original design's architecture section. Check each against plan.md and tasks.md. Flag any component without an implementation task.

5. **NFR preservation:** Compare NFRs from requirements.md against tasks.md. Flag any NFR (performance, security, scalability) not addressed in any task.

6. **Depth density check:** For each task in tasks.md, count the words in each task's description (excluding the task ID and file path header). If the average word count per task across ALL tasks is <80 words, this indicates high probability of depth loss (stub-level tasks with no algorithmic specification). Flag for CRITICAL regeneration.

**If any flag is raised, determine regeneration scope by severity:**
1. **CRITICAL — Full regeneration required** (triggered by any of):
   - FR count mismatch >10% (source FRs vs output FRs)
   - Any design section heading from source has NO counterpart in output plan.md
   - Any data entity from design appears in NO task
   - These require re-running the affected Speckit command(s) from scratch with more specific depth-preservation instructions
2. **MODERATE — Targeted regeneration required** (triggered by any of):
   - FR count mismatch 1-10%
   - Entity/NFR appears in data-model.md but not in tasks.md
   - These require re-running only the tasks generation with explicit instructions to add the missing items
3. **LOW — Manual patch acceptable** (triggered by any of):
   - Single NFR not addressed in a single task
   - Single edge case missing from a task description
   - These can be fixed by editing the specific task description directly without re-running Speckit commands

Document which source sections were lost and apply the appropriate regeneration scope. Only proceed to Phase 6 when depth verification passes.

#### 5c. Constitutional Alignment (NEW)

Read `references/constitution.md` and the project's `.specify/memory/constitution.md` (if present). Verify:

- Are all output documents faithful to the source materials? (Constitution Section V)
- Is provenance recorded for every artifact? (Constitution Section V)
- Does the plan keep the core deterministic and the agentic layer advisory? (Constitution Section IV)
- Are preview/reversible/non-destructive change principles reflected in the deployment design? (Constitution Section III)

Document any constitutional violations as amendments to the relevant output document.

### Phase 6: Delivery and Handoff

1. **Present all files** to the user:
   - `spec.md`, `plan.md`, `tasks.md`
   - `research.md`, `data-model.md` (if generated)
   - Original `requirements.md` and `design.md` (preserved as-is)

2. **Provide a delivery summary:**
   - Mode used (A/B/C) and rationale
   - Depth verification results — what passed, what was regenerated
   - FR count from source vs output (must match within tolerance)
   - Design section coverage (must be 100%)
   - Any `[NEEDS CLARIFICATION]` markers that remain
   - Constitutional alignment status

3. **Report any depth flags that required manual resolution:**
   - Which Speckit commands were re-run and why
   - Which design sections were hardest to preserve
   - If any content could not be preserved, document the specific sections and reason

4. **Suggest next steps:**
   - Review generated tasks.md — each task should be detailed enough to start implementation without re-reading the design document
   - Start implementation with Phase 1 tasks
   - Use `/speckit-implement` to execute the task pipeline
   - If task descriptions are still too shallow: re-run Phase 4 with more specific depth-preservation instructions

5. **Agent team handoff:**
   - The output files contain all context needed for implementation
   - A new coding session can pick up from tasks.md without this conversation's context
   - Each task in tasks.md is self-contained with implementation specification, not just a file path

6. **Iterative refinement path:**
   - User can return with new information at any phase
   - Depth verification (Phase 5b) can be re-run after any modification
   - If Speckit commands are re-run, depth-preservation directives must be re-applied
   - The constitution governs all amendments — review before any change

## Compatibility Notes

### SpecKit Alignment
- This skill targets Speckit commands DIRECTLY instead of generating documents from external templates
- Speckit commands (e.g., `/speckit-specify`) are defined as SKILL.md instruction files in `.agents/skills/speckit-*/`. They may or may not be accessible as executable slash commands depending on the agent environment
- **If executable as slash commands:** invoke them directly with depth-preservation directives
- **If NOT executable (SKILL.md files only):** read each Speckit SKILL.md and implement its instructions manually, applying the depth-preservation directives from Phase 4 to every output
- The output directory targets `specs/{NNN}-{feature-name}/` (Speckit convention) wherever possible
- **Depth preservation is NOT automatic** — whether invoking or implementing manually, every Speckit command MUST include the [DEPTH-PRESERVATION DIRECTIVE] blocks from Phase 4
- **Skill v2 replaces the old "manual template generation" approach** — all generation flows through the Speckit pipeline (invoked or implemented)

### OpenSpec Alignment
- Requirements use SHALL/MUST language
- Design follows proposal + design.md pattern
- Data entities described as capabilities
- Testable scenarios per requirement

### Kiro/Cursor Alignment
- All output files are self-contained markdown
- No external dependencies or tool-specific syntax
- Compatible with any agent that reads markdown specs

## Anti-Patterns

- **Never** skip prior art research (Phase 2) — except in Mode C
- **Never** include technology choices in requirements.md
- **Never** generate a constitution.md from scratch — use the user's existing one or reference the skill's `references/constitution.md`
- **Never** use dates/timestamps in implementation phases
- **Never** skip deliberative refinement (Phase 5)
- **Never** write code in any spec document
- **Never** leave a functional requirement without acceptance criteria
- **Never** assume the user's stack without checking preferences/context
- **Never** inflate confidence scores to skip clarification rounds
- **Never** write exploration/research findings to output files (they are process context, not artifacts)
- **Never** ask all discovery questions in a single message (sequential categories, 2-4 questions each)
- **Never** proceed past the confidence gate without explicitly confirming with the user
- **CRITICAL: Never** call a Speckit command without a [DEPTH-PRESERVATION DIRECTIVE] block — this is the single most important rule of v2. Without it, Speckit will compress the input and lose detail.
- **CRITICAL: Never** assume `/speckit-specify`, `/speckit-plan`, and `/speckit-tasks` are executable slash commands. They are SKILL.md instruction files in `.agents/skills/speckit-*/`. Always check if they are available as slash commands first. If not, read the SKILL.md file and implement the logic manually with depth-preservation directives applied.
- **Never** accept Speckit command output without running the depth-verification gate (Phase 5b)
- **Never** skip constitution compatibility check — run it before final delivery
- **Never** let Speckit truncate FRs due to template limits — extend the template rather than drop content
- **Never** regenerate requirements.md and design.md from templates when they already contain detailed content — always preserve the source depth
